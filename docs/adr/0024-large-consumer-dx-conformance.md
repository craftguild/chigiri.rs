## 1. Context

The existing 70-object, 750-field consumer checks generated size, MSRV and
stable compilation, Clippy, and rustdoc, preventing code-generation regressions
on wide schemas. It focuses on generation and compile performance and does not
exercise projection authoring, doctor diagnostics, the independent rate-provider
crate, and the new crate graph together in one gate.

Small books examples cannot expose combined regressions in generation volume,
IDE and rustdoc surface, diagnostic correlation, and provider dependency
boundaries. Using an external application as the sole oracle would optimize the framework for
product-specific domain and security policy, so the repository-owned synthetic
consumer is strengthened instead.

## 2. Decision

### 2.1 Canonical fixture

`tests/fixtures/vnext-large-product` remains the canonical large consumer and
has at least this shape:

| Element | Minimum |
| --- | ---: |
| object | 70 |
| field | 750 |
| input object | 19 |
| domain-bound enum | 65 |
| custom scalar | 5 |

The fixture includes Query and Mutation roots; projection fields without
arguments; fields with arguments, async work, and errors; lists and nullability;
interfaces and unions; custom scalars; and domain enum bindings. It copies no
product source, credentials, personal data, or application-specific types or policies.

Roots use complete resolver traits. Non-root objects exercise both complete
traits and projection plans. The fixture does not hide field completeness in a
macro merely to reduce line counts: application-facing assembly and
representative object implementations remain reviewable ordinary Rust. A
bounded macro or script with an explicit responsibility may generate large
amounts of synthetic data with identical shapes.

### 2.2 One conformance entry point

`scripts/check-large-consumer-conformance.sh` is the supported entry point and
subsumes the existing `check-large-consumer-performance.sh`. The old script name
is not kept as a shim; repository, CI, and runbook callers migrate together.

Using a clean temporary target/work directory and the committed lockfile, the
script collects results from all applicable commands before deciding, rather
than failing at the first independent error. It does not continue to misleading
compilation after a prerequisite generation or drift failure.

1. Generate from schema/configuration and check drift.
2. Check ADR-0020 scaffold determinism, source order, and placeholder safety.
3. Run `cargo pythia doctor` on the positive consumer.
4. Run fmt, check, test, Clippy with `-D warnings`, and rustdoc with
   `-D warnings` on MSRV 1.85 and current stable.
5. Check generated byte/file/line budgets and the public rustdoc surface.
6. Compile and run conformance for a third-party `pythia_rate` provider fixture.
7. Run the same provider conformance for all four official ADR-0023 providers.
8. Run negative consumer diagnostic fixtures.

### 2.3 Negative diagnostic matrix

Each case applies one mutation to a temporary copy and never edits the tracked
fixture directly:

- Remove the next `with_<object>` from resolver assembly.
- Remove one field from a projection chain.
- Swap the order of projection fields.
- Change a `project_*` return to an incorrect scalar, list, or nullability type.
- Remove one root trait method.
- Change one byte in a checked-in generated file.
- Change the generated ABI guard to a value other than 5.

Each case checks doctor exit 1, the original rustc or Pythia diagnostic, the
exact supplemental code such as `SF4018` or `SF4019`, the GraphQL coordinate,
and the correction method. Snapshots exclude complete rustc text, private shard
file numbers, hashes, and toolchain-specific wording. A case never combines two
mutations.

### 2.4 Provider consumer matrix

The third-party fixture has only `pythia_rate` as a normal dependency; it does
not depend on HTTP, runtime, the façade, or the official memory crate. It may use
testkit conformance as a development dependency. The fixture implements one
atomic in-memory fake provider and passes the positive suite.

A separate negative fixture or test-only provider independently implements
non-atomic consumption, a blocking poll, a malformed decision, and a future that
cannot be dropped; the suite must reject each. All four official providers run
the same common suite. Algorithm-specific tests alone do not establish SPI
conformance.

### 2.5 Fixed thresholds and evidence

The following thresholds are fixed before results are observed:

| Gate | Threshold |
| --- | ---: |
| generated directory total | At most 64 MiB |
| generated/application/repository `.rs`/`.sh` | At most 400 physical lines each |
| each MSRV/stable fmt/check/test/Clippy/rustdoc command | At most 180 seconds |
| positive large-consumer doctor | At most 180 seconds |
| one-object scaffold | At most 30 seconds and 64 MiB |
| diagnostic count per negative case | Within the existing compiler limit; at most one Pythia supplement |

Time gates measure elapsed duration with a monotonic clock and terminate and
wait for the process group on timeout. The 180-second threshold accounts for CI
host variation and is never learned or relaxed automatically after a slow run.
Because rust-analyzer completion latency varies widely with environment and
cache state, it has no numeric gate. Public rustdoc, hidden-item scans, and
compile fixtures for the current typestate stage are stable proxies for IDE
surface.

Evidence JSON records format version, HEAD, dirty flag, toolchain, command argv,
exit status, elapsed duration, generated bytes/files/maximum lines,
doctor/scaffold results, and every acceptance ID. A latest pointer and
revision-specific artifact follow existing safe-publication rules. Evidence JSON
is not committed as a source-controlled baseline.

### 2.6 Scope boundary

This gate covers developer scalability and contract conformance. It does not
replace release evidence for request throughput, latency, RSS soak, or long
fuzzing. After ADR-0022 and ADR-0023 implementation, Gates P-D and P-E remain
Not Passed until formal benchmarks, load/soak tests, and long fuzz runs are
reacquired through the manual runbook.

## 4. Consequences

### Positive

- The gate catches regressions in user-facing diagnostics and provider
  integration, not only code-generation scale.
- Scale lessons from an external application become a framework gate without importing
  product-specific contracts.
- Public surface, compile time, and generated size are comparable for the same
  revision.

### Negative

- Testing both MSRV and stable plus the negative doctor matrix increases CI time.
- The synthetic fixture and expected diagnostic coordinates must track schema
  changes.
- Actual rust-analyzer latency is not automatically guaranteed.

## 5. Rejected alternatives

- Use only the books examples as the developer-experience oracle: schema width
  and generated-surface regressions remain invisible.
- Use an external application as the CI fixture: the gate depends on product policy, private source,
  and another repository's availability.
- Snapshot complete rustc output: snapshots are fragile across stable toolchains.
- Measure only generated bytes: failures in doctor, public API, and provider
  boundaries are missed.
- Add formal request benchmarks to this gate: developer compilation and manual
  release evidence have different responsibilities.
